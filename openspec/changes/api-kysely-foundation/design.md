# Design

## Context

See proposal.md for motivation and scope. Current state that shapes the approach:

- Every service except a few custom ones is created by `feathers-objection` (`createService({ model, whitelist, paginate, allowedEager })`). That library translates the Feathers query syntax to Objection, builds the `{ total, limit, skip, data }` page envelope, serialises the models' virtual attributes (`type`, `link`), and maps Objection and DB errors to Feathers errors (`ValidationError` → `BadRequest`, unique violation → `Conflict`, and so on).
- Validation runs inside the Objection models: `BaseModel` plugs a Joi validator into Objection, and `objection-db-errors` wraps Postgres errors.
- Authentication and authorisation are app-level hooks in `src/app.js` (`authenticate('jwt')` + `authorize`); they are independent of the data layer except that `authorize`'s `fetchResource` calls `service.get(id, { query: { $eager } })` for scopes that need the stored resource.
- `packages/admin` talks to `/admin/*` through `ra-data-feathers`; that wire contract stays (decided: keep it; replacing the data provider is a separate future change).
- `packages/api` runs from source on native ESM with no build step (Node 24.x). Migrations are knex `.js` files tracked by name, including the extension, in `knex_migrations`; `npm run migrate:latest` is the Dokku predeploy hook.
- The integration tests drive services through `app.service(...)` and HTTP against a shared testcontainer. They are the regression net for this refactor.

## Goals / Non-Goals

**Goals:**

- Establish the target layering and its conventions on real resources, so later changes copy a proven pattern instead of designing one.
- Make generated database types the source of typing for repositories.
- Keep every migrated endpoint byte-compatible for clients: paths, methods, response shapes, status codes and error codes.

**Non-Goals:**

- Changing the schema or the migration workflow.
- Removing Objection; it stays until the users/auth step.
- Changing validation libraries; Joi schemas move layers but stay Joi.
- Converting existing `.js` files that this change does not otherwise touch.

## Decisions

### Layering

```
  Feathers service (controller)         src/services/<name>.ts
     |  maps params/query <-> domain calls; no SQL, no business rules
     |  app-level hooks (authenticate, authorize, logError) unchanged
     v
  Domain                                src/domain/<name>.ts
     |  validation (Joi), business rules, transactions, side effects
     v
  Repository                            src/repositories/<name>.ts
     |  Kysely queries only, typed rows, named filters
     v
  Postgres
```

- Every layer is an object factory named after its layer: `createProductsRepository(db)`, `createProductsDomain(db)` and `createProductsController(db)`. Each factory takes `db` and builds the layer below it; only the database is injected, because it is the one real dependency (pool and transactions) and tests replace the database, not layers. "Service" only ever means a Feathers service: `src/services/` holds a controller plus its `app.use` registration and hooks.
- Controllers are plain objects that implement only the Feathers methods the resource exposes. A missing method replaces `disallow()`, and `disallow('external')` remains as a hook where internal callers still need the method.
- Domains receive plain arguments (`list(options)`, `create(input)`), not Feathers `params`, so they are callable from jobs and tests without the Feathers runtime.
- Repositories accept an optional transaction (`Kysely<DB> | Transaction<DB>`) so a domain can compose several of them atomically.
- `src/domain/` is used instead of a second `services/` folder because `src/services/` already means Feathers services.
- Alternative considered: keep `feathers-objection`'s generated services and only swap the model layer underneath. Rejected because the generated services are exactly the coupling this effort removes.

### Kysely with knex as the migration runner

- One Kysely instance (`src/db/kysely.ts`) with `PostgresDialect` and `CamelCasePlugin`, so rows keep the camelCase keys that `knexSnakeCaseMappers` produces today.
- DB types are generated by `kysely-codegen --camel-case` into `src/db/types.ts` from a freshly migrated database. Codegen reads its connection from `postgres.connection` in `config/default.json`, like `db/knexfile.js` does, so the workflow needs no extra environment variable. An npm script (`db:types`) runs codegen; regenerating after every new migration becomes part of the migration workflow and is documented next to `migrate:make`.
- Existing migrations stay untouched, and new migrations remain knex migrations.
- Alternatives considered: Drizzle, which would make a TypeScript schema the source of truth and need a baseline against the production schema with a second migration history. Plain knex was rejected because it gives no useful row types.

### TypeScript without a build step

- `tsconfig.json`: `allowJs`, `checkJs: false`, `noEmit`, `strict`, `module`/`moduleResolution: nodenext`, `erasableSyntaxOnly`, `allowImportingTsExtensions`, `verbatimModuleSyntax`. `tsc --noEmit` runs as a `typecheck` script and joins lint/CI.
- Relative imports name the real file: `./products.ts` from TypeScript, and `.js` files importing a converted module switch to the `.ts` specifier.
- Node 24 strips types natively, so `node src/index.js` keeps working when `src/index.js` imports `.ts` modules. The entry point stays `.js` in this change.
- Erasable syntax only: no `enum`, no parameter properties, no `namespace`.

### Feathers query translation (admin)

- `src/db/feathersQuery.ts` applies an already-parsed Feathers query to a Kysely `SelectQueryBuilder` for a per-resource **allowlist of columns**: equality, `$in`, `$ne`, `$ilike`, `$sort`, `$limit` and `$skip`. `$ne` is there because the admin's user form filters the origins it offers with `origin[$ne]=default`. Anything else, such as unknown columns or `$select`, `$eager`, `$modify`, `$joinRelation` or `$or` from clients, is rejected with `BadRequest`.
- Parsing of `$limit`, `$skip` and `$sort` reuses `filterQuery` from `@feathersjs/adapter-commons`, already a transitive dependency and promoted to a direct one, so paging defaults behave as before: `paginate.default` 50, and no max, matching today.
- `$select` is rejected rather than supported. `feathers-objection` accepts it today, but `ra-data-feathers` never sends it, so like `$eager` it is dropped instead of carried forward unused; a silently ignored `$select` would return a different field set without telling the caller.
- The paged find returns `{ total, limit, skip, data }`, with the count taken from the same filtered query before limit and offset are applied.
- Server-side admin filters that today use `$modify` and `$joinRelation` (`hasBadge`, `notHasBadge`, `hasOrigin`, `roles.id`) become named repository filters when their resources migrate. None of them belong to the lookup resources.

### Errors

- `src/db/errors.ts` maps `pg` errors by SQLSTATE to the Feathers errors `feathers-objection` produces today. For example, 23505 unique and foreign-key violations become `Conflict`, and not-null, check and invalid-text violations become `BadRequest`. Joi failures become `BadRequest` with the same `errors` payload. The exact mapping is copied from `feathers-objection`'s error handler, not reinvented.
- Domains raise `NotFound` for a missing id, as `get` and `patch` do today.

### Response shape

- Domains add `type` and `link`, the former Objection virtual attributes, to every returned record. A small helper per resource keeps the rule in one place.
- Public lookups keep the existing `filterAllowedFields` after-hook. It belongs to the authorisation layer, not the data layer.

## Risks / Trade-offs

- [Two pools, so no cross-library transaction] → A resource's whole read and write path migrates in one go. Lookups have no writes that span Objection-owned tables. Pool sizes are kept small so the combined connection count stays within the Postgres limit.
- [Subtle response drift, such as key casing, `type`/`link`, null vs. missing fields, or number vs. string for numerics] → Before rewriting, add characterisation tests for each migrated endpoint (public and admin `find`/`get`, admin `create`/`patch`/`remove`) that assert the full response body. They must pass both before and after.
- [`ra-data-feathers` sends an operator the translator does not support] → First task: inventory the operators it emits, from library source and logged admin requests, and lock them into the translator's tests. Unknown operators fail loudly with `BadRequest` instead of being silently ignored.
- [Mixed `.js`/`.ts` breaks vitest, `node --watch` or the Dokku start] → Verify all three in step 0, before any resource moves. Rollback is a plain revert, since nothing about the schema changes.
- [`authorize`'s `fetchResource` passes `$eager` to `service.get`] → Not exercised by the lookup resources. Recorded for the entries step, where the controller must honour or replace it.
- [Objection relation mappings still reference `Product`, `Badge`, `Goal` and `Role` models] → Those model classes stay until their last Objection consumer is migrated. Only the services move now.

## Migration Plan

This change is steps 0 and 1 of the overall roadmap. Each later step is its own change:

```
  0. Foundation   tsconfig + typecheck, Kysely instance, codegen,
                  error mapper, query translator       <- this change
  1. Lookups      products, goals, badges (+ admin), roles, origins
                                                       <- this change
  2. Entries      farms, depots, initiatives, entries, search index;
                  atomic relation writes; authorize/fetchResource
  3. Jobs/admin   stats, audit, campaigns, messages, bounces, jobs
  4. Users/auth   user repository behind a Feathers-shaped users
                  service (LocalStrategy, JWTStrategy,
                  authentication-management depend on it)
  5. Removal      objection, feathers-objection, objection-db-errors,
                  BaseModel, knexSnakeCaseMappers
```

Deployment needs no schema change and no data migration. Rollback is a git revert and redeploy.

## Open Questions

- Pool sizing for the two pools in production, to confirm against the Dokku Postgres `max_connections`.
- Whether `type`/`link` should eventually leave admin responses (react-admin ignores them). That is deferred to the admin data-provider change.
