# Spec: API ORM Modernization

## Problem Statement

`packages/api` persists all data through [Objection.js](https://vincit.github.io/objection.js/)
and the `feathers-objection` adapter. Both are end-of-life: `feathers-objection@7.6.0`
carries an explicit npm deprecation notice ("Deprecated since Objection.js is no longer
maintained"), and `objection@3.1.5` has had no release since September 2024. Nothing is
broken today — there is no CVE and no runtime failure — but the API is pinned to two
unmaintained packages that sit directly between the app and its database, and that
position gets progressively more expensive as Node and `knex` majors move on.

The dependency is only half the problem. `feathers-objection` generates CRUD services
whose query surface is open by default, and the codebase has already paid for that: the
comment at `src/services/entries.js:16-22` documents a real leak where a client-supplied
`$eager` let anonymous callers traverse into the `ownerships` relation and read password
hashes and private address fields. Field-level access control is applied _after_ the
database has already returned the data (`src/hooks/filterAllowedFields.js:8-15` deletes
keys from the result object), and business logic is spread across long implicit-ordered
hook chains — `src/services/farms.js:79-101` has twelve after-hooks whose correctness
depends on undocumented ordering, one of which (`relate`, `src/hooks/relations.js:75-98`)
swallows its own errors and returns HTTP 200 on a failed relation write.

This spec replaces the ORM layer and, for the public API, the architecture around it:
admin services keep generated CRUD on the officially maintained `@feathersjs/knex`
adapter, while the public services move to an explicit repository layer where the SQL
select list _is_ the field allow-list. The migration is staged so every step ships
independently with a green test suite, and the public JSON contract does not change at
any point.

**Runtime**

- Local Node is **v24.16.0**, and `node some-file.ts` was verified to execute TypeScript
  directly with no build step. `package.json#engines` already pins `node: 24.x`.
- `packages/api` runs from `src` on native ESM with **no build step** — babel was removed
  deliberately in commit `067068b1` ("chore(api): run on native ESM and drop babel").
  Preserving this property is a hard constraint of the TypeScript work.

**Current ORM coupling**

- 18 services are generated by `feathers-objection`'s `createService`:
  - **7 public**: `farms`, `depots`, `initiatives`, `users`, `goals`, `products`, `badges`
  - **11 admin**: `admin/{farms, depots, initiatives, users, goals, products, roles,
badges, origins, emailCampaigns, emailMessages}`
  - Of these, 8 declare `allowedEager` (`farms`, `depots`, `initiatives`, `users` — in
    both their public and admin variants); the other 10 are relation-free.
- Additional hand-written services already using the Objection query builder directly:
  `entries`, `autocomplete`, `admin/entries` (`User.relatedQuery(...).for(...)`),
  `admin/stats`, `admin/audit`.
- Other direct call sites: `src/hooks/email.js:57` (`withGraphFetched('users.[adminOrigins]')`),
  `src/jobs/importEmailBounces.js:37`, and `src/jobs/{createLoginReminders,
createSecondLoginReminders,flagInactiveUsers}.js` (which already use raw
  `BaseModel.knex()` and are therefore nearly ORM-free).
- Objection-specific features in use, all of which need a replacement:
  `$eager`/`allowedEager`/`eagerFilters`, `$joinRelation`, `$modify` + model `modifiers`
  (`src/models/farms.js:78-119`), `upsertGraph` with `relate`/`unrelate`
  (`src/hooks/relations.js:82,110`), the Joi `Validator` wired into the model layer
  (`src/models/base.js:6-28`), `virtualAttributes` `type`/`link` (load-bearing —
  `relateOwner` dispatches on `ctx.result.type()`), `$formatJson` secret stripping on the
  `User` model (`src/models/users.js:31-35`), and `objection-db-errors`.
- `knexSnakeCaseMappers` (`src/db.js:9`) is **knex-level** configuration, so it survives
  an adapter swap untouched. The whole app speaks camelCase; the database is snake_case.

**Client query surface**

- `packages/admin` is react-admin 5 via `ra-data-feathers`. Its filter surface is
  irreducibly generic: `src/resources/farms.jsx` alone exposes ~20 filterable fields, there
  are ~150 filter inputs across the 13 resource files, and every list column is sortable.
  This is why admin keeps a generic adapter.
- Admin list/get responses return relations as **plain ID arrays by default** —
  `src/hooks/admin.js:16-32` (`mapResultListRelationsToIds`) flattens the eager result —
  with full nested objects only when `$details=true`.
- The public clients (`packages/map`, `packages/embed`) consume fixed response shapes and
  do not drive generic filtering. No client sends `$eager`, `$joinRelation` or `$modify`
  of its own.

**Authorization**

`src/permissions.js` defines the per-role readable/writable field matrix that
`src/hooks/authorization.js` turns into `ctx.allowedFields`. It remains the authoritative
source for field-level access control throughout this migration; repositories must stay
consistent with it rather than replacing it.

**Test baseline**

- 119 test cases across 13 files, run by vitest against a **real Postgres** started by
  testcontainers (`db/globalSetup.js`, `db/integrationTestSetup.js`).
- `vitest.config.js` currently matches `src/**/*.test.js` only.
- Covered: `depots`, `entries`, `farms`, `initiatives`, `users`, `autocomplete`,
  `authentication`, `authManagement`, `rateLimit`, `cors`, error-code contracts, FK schema.
- **Not covered: any `admin/*` service.** These carry the densest adapter-specific
  behaviour (`$modify`, `$joinRelation`, `$ilike`, pagination, relation-ID flattening).

## Features

1. **API response contract test coverage**
   - Description: Before any code moves, lock the observable HTTP behaviour of every
     service that this migration touches, so each later stage is verified by diffing
     against a recorded baseline rather than by inspection. This is the prerequisite for
     Features 5-8 and the single largest risk reducer in the spec. Tests run against the
     existing testcontainers Postgres and assert on serialized HTTP responses — status
     code, pagination envelope, key set, nesting shape, and ordering — not on internal
     model or query-builder behaviour.
   - Acceptance criteria:
     - Every public endpoint has response-shape coverage: `farms`, `depots`,
       `initiatives`, `users`, `entries`, `goals`, `products`, `badges`, `autocomplete`.
     - Every adapter-generated `admin/*` service (all 11) has `find` and `get` coverage,
       including: the `{ total, limit, skip, data }` pagination envelope, default
       relation-as-ID-array output, and the `$details=true` nested variant.
     - The hand-written admin services migrated in Feature 8 have response-shape coverage
       too: `admin/entries`, `admin/stats` and `admin/audit`.
     - The `$modify`-driven admin filters are covered: `hasBadge`, `notHasBadge`, and the
       non-superadmin `hasOrigin` origin scoping (`src/hooks/admin.js:60-80,97-111`).
     - The `$joinRelation` path is covered: filtering `admin/users` by `roles.id`.
     - `$ilike` fuzzy search is covered for at least one entry resource and one user
       resource, including the `q` parameter path.
     - Field-level access control is covered for at least `farms` and `depots` in three
       states — anonymous, authenticated non-owner, authenticated owner — asserting that
       `address`, `street` and `housenumber` appear only for the owner.
     - A regression test asserts that no response from any public endpoint ever contains
       `password`, `verifyToken`, `verifyShortToken`, `verifyChanges`, `resetToken` or
       `resetShortToken`, including inside nested relations.
     - `entries` coverage includes both the anonymous listing and the `mine` variant, and
       asserts the GeoJSON envelope produced by `toGeoJSON`.
     - A coarse regression guard exists on the hottest read paths — `entries` and the
       `farms` listing — asserting an upper bound on the number of SQL statements issued
       per request (recorded against the current implementation as the baseline) and,
       optionally, a generous wall-clock ceiling. The intent is only to catch an N+1 or a
       full-table-scan regression introduced by the migration; it is not a benchmark, and
       the bounds should be loose enough not to flake on CI. Statements can be counted via
       knex's `query` event, or Kysely's log/plugin hook if Feature 6 selects Kysely.
     - Relation-write behaviour is covered: creating and patching a farm with `products`,
       `badges` and `depots` returns the expected related IDs, and the owner is related on
       create.
     - Existing error-code tests continue to pass unchanged; DB-constraint violations
       (unique, foreign key, not-null) each have an asserted HTTP status and error code.
     - The suite passes against the current Objection implementation before any migration
       work begins, and is treated as the acceptance gate for Features 5-8.

2. **TypeScript toolchain with no build step**
   - Description: Introduce TypeScript for typechecking only, relying on Node 24's native
     type stripping so the package keeps running directly from `src` (see Verified
     Environment Facts). Convert the ORM-free parts of the codebase now; leave models and
     services in JavaScript until the stage that migrates them, so no effort is spent
     typing code that is about to be deleted.
   - Acceptance criteria:
     - `tsconfig.json` exists with `noEmit: true`, `module: nodenext`,
       `allowImportingTsExtensions: true`, `erasableSyntaxOnly: true`, `allowJs: true`,
       `strict: true`; `checkJs` starts `false`.
     - `npm start` and `npm run dev` still invoke `node` directly on sources — no bundler,
       transpiler or build artifact is introduced, and the Dockerfile/Procfile gain no
       build step.
     - A `typecheck` script exists and passes, and runs in CI.
     - `src/{app,index,logger,permissions}.ts`, `src/middleware/**`, `src/utils/**`,
       `src/jobs/**` and the ORM-free files in `src/hooks/**` are TypeScript.
     - `vitest.config.js` matches both `.js` and `.ts` test files.
     - No enums, namespaces, parameter properties or decorators are introduced anywhere
       (required by Node's erasable-syntax-only constraint).
     - The full test suite from Feature 1 passes unchanged after conversion.

3. **Generated database types (Kanel)**
   - Description: Derive TypeScript types from the live Postgres schema with Kanel so the
     knex migrations remain the single source of truth and no parallel schema definition
     is hand-maintained. Generated types are committed and drift-checked in CI.
   - Acceptance criteria:
     - Kanel is configured against the same database the migrations produce, and its
       output is committed under `src/db/`.
     - A documented npm script regenerates the types; running it after `migrate:latest`
       on an up-to-date database produces no diff.
     - CI fails if the committed types differ from a fresh generation (drift check).
     - Generated identifiers are camelCase, matching the `knexSnakeCaseMappers` convention
       the application already uses.
     - At least one consumer imports the generated types, proving the wiring.

4. **Extract ORM-agnostic concerns off the Objection models**
   - Description: Move the cross-cutting behaviour that currently lives inside Objection
     model classes into plain hooks/utilities, while still running on Objection. This
     stage is independently shippable, changes no observable behaviour, and shrinks the
     later swaps to pure data-access changes.
   - Acceptance criteria:
     - Joi validation runs as a service-level before hook using the existing schemas in
       `src/models/validation/`, not via Objection's `Validator`; the patch-skips-validation
       behaviour of `src/models/base.js:8` is preserved.
     - The `type` and `link` virtuals are produced outside the model layer, and every
       consumer that currently calls `.type()` — including `relateOwner` and
       `filterOwnedEntries` — works against the new mechanism.
     - `User` secret stripping no longer depends on `$formatJson`; the Feature 1
       no-secrets regression test still passes.
     - Database error mapping is implemented over raw `pg` error codes (`23505` unique,
       `23503` foreign key, `23502` not-null) rather than `objection-db-errors`;
       `db-errors` is **not** added as a dependency. All existing error-code tests pass
       unchanged.
     - `src/models/base.js` no longer contains validation, serialization or error-mapping
       logic.

5. **Migrate admin services to `@feathersjs/knex`**
   - Description: Replace `feathers-objection`'s `createService` with the officially
     maintained `KnexService` for all 11 adapter-generated `admin/*` services, keeping
     generated CRUD and the generic query surface react-admin depends on. Relation loading
     is simpler here than on the public side because admin returns relation ID arrays by
     default.
   - Acceptance criteria:
     - All 11 `admin/*` adapter services are constructed with `KnexService` against the
       existing knex instance; none imports `feathers-objection`.
     - `$ilike` works via the adapter's `operators`/`extendedOperators` configuration.
     - `$modify` (`hasBadge`, `notHasBadge`, `hasOrigin`) is reimplemented via
       `createQuery` overrides and/or `params.knex`; the existing `whereExists` SQL from
       `src/models/farms.js:78-119` is preserved in behaviour.
     - `$joinRelation` for the `roles.id` filter on `admin/users` is reimplemented.
     - Relation IDs are loaded with a batched join-table query — no N+1 — and `$details=true`
       still returns nested objects.
     - `knexSnakeCaseMappers` is verified to work with `KnexService` on the first migrated
       service before the rest follow.
     - Every admin test from Feature 1 passes without modification to its assertions.
     - `packages/admin` requires no changes; its lists, filters, sorting, pagination,
       edit forms and delete actions are verified working against the migrated API.

6. **Repository layer pilot on `depots`, with the query-builder decision**
   - Description: Establish the explicit repository pattern on the smallest public service
     that still exercises nested many-to-many (`farms.[products]`), and use it to settle an
     open decision: whether the repository layer uses **knex + Kanel types** or **Kysely +
     `kanel-kysely`**. `depots` is implemented both ways, the two are compared on the same
     passing tests, one is chosen, and the other is deleted. The outcome binds Features 7
     and 8. Admin services stay on knex regardless of the outcome.
   - Acceptance criteria:
     - A `src/repositories/` layer exists whose functions take explicit domain arguments
       (e.g. `findActiveDepots({ withDetails })`), never a Feathers `params.query`.
     - The `depots` Feathers service is hand-written and thin: authentication, validation,
       serialization and hook wiring only, delegating all data access to the repository.
     - The select list in the repository is the field allow-list — no post-hoc key deletion
       is relied upon for the fields the repository controls — and it is consistent with
       `src/permissions.js`.
     - Nested `farms.[products]` and `ownerships` are loaded without N+1, with per-relation
       column allow-lists equivalent to today's `eagerFilters`.
     - Both variants are implemented and both pass the unmodified Feature 1 `depots` tests,
       including the field-level access-control and no-secrets assertions.
     - The decision is recorded at `specs/api-orm-modernization/decision-query-builder.md`,
       covering at minimum: type safety actually observed, the ergonomics
       of nested many-to-many loading, whether a second connection pool is warranted, and
       whether the camelCase mapping (`knexSnakeCaseMappers` vs Kysely's `CamelCasePlugin`)
       stays consistent across the two stacks serving the same tables.
     - Only the chosen variant remains in the codebase at the end of this feature.
     - If Kysely is chosen: `kanel-kysely` generates its `Database` interface from the same
       Kanel run as Feature 3, knex migrations remain the only schema tooling, Kysely's own
       migration facility is not used, and explicit pool limits are set on both pools.

7. **Migrate the remaining public services to repositories**
   - Description: Apply the pattern chosen in Feature 6 to the other public services, one
     at a time, each gated by its Feature 1 tests. This also removes the last uses of
     `upsertGraph`.
   - Acceptance criteria:
     - `farms`, `initiatives`, `users`, `goals`, `products` and `badges` are served by
       hand-written services over repositories; none imports `feathers-objection`.
     - `upsertGraph`-based relation syncing (`src/hooks/relations.js:75-122`) is replaced by
       explicit join-table synchronization that runs **inside the create/patch transaction**,
       so a failed relation write fails the request instead of logging and returning 200.
     - The implicit hook ordering in `src/services/farms.js:79-101` is resolved: relation
       writes and notification/search-index side effects are sequenced explicitly rather
       than by hook array position.
     - Every public response-shape test from Feature 1 passes with unmodified assertions.
     - `packages/map` and `packages/embed` are verified working against the migrated API.

8. **Migrate the remaining direct Objection call sites**
   - Description: Port the hand-written services and hooks that use the Objection query
     builder directly.
   - Acceptance criteria:
     - `entries`, `autocomplete` (including the `to_tsquery`/`ts_rank` full-text query on
       `entries_search`), `admin/entries` (currently `User.relatedQuery(...).for(...)`),
       `admin/stats` and `admin/audit` no longer reference Objection.
     - `src/hooks/email.js:57` and `src/jobs/importEmailBounces.js:37` no longer reference
       Objection; the jobs that already use `BaseModel.knex()` are repointed at the shared
       database module.
     - The `entries` endpoint's fixed server-side relation loading and its owner-only column
       handling are preserved exactly as documented at `src/services/entries.js:16-22`.
     - `autocomplete` still escapes user input before building the `tsquery` and still caps
       input length, with the existing tests passing.

9. **Remove the Objection dependencies**
   - Description: Delete the ORM layer and its dependencies once nothing imports them.
   - Acceptance criteria:
     - `objection`, `feathers-objection` and `objection-db-errors` are absent from
       `packages/api/package.json` and from the lockfile.
     - No file under `packages/api/src` imports any of the three.
     - `src/models/` contains no Objection model classes; anything still needed from it
       (relation maps, column lists) lives in the repository or type layer.
     - The full suite passes and the app boots and serves requests with the dependencies
       removed.

## Technical Solution

- **Architecture — split by query surface, not by ORM.** The admin API needs a generic,
  client-driven filter/sort/paginate surface (react-admin), so it keeps generated CRUD on
  `@feathersjs/knex`. The public API has a small, fixed, security-sensitive surface, so it
  moves to explicit repositories with Feathers reduced to transport, authentication and
  cross-cutting hooks. Layering for the public side is `service → repository → database`,
  with repositories taking explicit arguments rather than Feathers query objects.
- **Technologies.** knex stays for migrations, for the admin adapter and (unless Feature 6
  decides otherwise) for repositories. Kanel generates types from the live schema. Kysely
  is a candidate for the repository layer only, decided by the Feature 6 pilot. TypeScript
  runs via Node 24 native type stripping with `tsc --noEmit` for checking.
- **Key decisions.**
  - `@feathersjs/knex` over the community `feathers-knex` (dead since 2022) — the former is
    Feathers 5 core and ships in lockstep with the framework already in use.
  - Drizzle was evaluated and rejected: it would require a hand-maintained schema DSL
    alongside the 38 existing knex migrations, creating permanent dual-schema maintenance
    and drift risk. Kanel derives types from the database instead, which keeps migrations
    authoritative. Kysely remains in contention precisely because it also has no schema DSL
    and no migration tooling of its own.
  - Repositories make the query-builder choice reversible, which is itself an argument for
    preferring the simplest option; this is why the Feature 6 decision is deliberately
    deferred to a measured pilot rather than settled up front.
  - Explicit selects replace post-hoc field deletion for repository-controlled fields, so
    the `entries.js` class of leak becomes structurally impossible rather than filtered
    after the fact. `src/permissions.js` stays authoritative for role-based field access.
  - No `db-errors` dependency: it is stale since 2022 and the mapping is ~20 lines of pg
    error codes.
- **Feature dependencies.** Feature 1 gates Features 5-8 and must land first. Features 2
  and 3 are independent of each other and of Feature 1, but both should land before 5-8 so
  migrated code is written in TypeScript against generated types rather than converted
  twice. Feature 4 must precede Features 5 and 7. Feature 6 gates Feature 7. Features 5 and
  7-8 are independent of each other and may proceed in either order or in parallel.
  Feature 9 is last.

## Out of Scope

- **Zod schema generation.** `kanel-zod` was discussed and is explicitly not part of this
  work. Joi remains the validation library; Feature 4 only moves where it runs.
- Replacing Joi with `@feathersjs/schema`/TypeBox, or any other validation-library change.
- Upgrading to Feathers 6 (currently `6.0.0-pre.0`).
- Changing the public HTTP contract in any way — no new endpoints, no changed response
  shapes, no changed query parameters. Any behaviour change discovered mid-migration is a
  bug to be fixed or a follow-up spec, not a licence to reshape the API.
- Changes to `packages/admin`, `packages/map` or `packages/embed` beyond verifying they
  still work.
- Database schema changes, new migrations for their own sake, and any performance work
  beyond what falls out of replacing eager loading with explicit queries. Benchmarking,
  load testing and query tuning are out of scope; the coarse statement-count guard in
  Feature 1 is the only performance assertion this spec asks for.
- Converting the entire API to TypeScript. Feature 2 converts the ORM-free files; models
  and services become TypeScript only as their migrating stage reaches them, and some `.js`
  will remain when this spec is complete.
- Rotating the committed JWT secret and other ops actions tracked separately.

## Additional Notes

- **Risks.**
  - The `admin/*` services have zero test coverage today and carry the most adapter-specific
    behaviour. Feature 1 is not optional groundwork; if it is skipped or thinned, Feature 5
    has no safety net.
  - `@feathersjs/knex` has no eager-loading concept. Relations are joins, `createQuery`
    overrides or resolver-style batched loads. Feature 5's acceptance criteria assume the
    batched join-table approach; confirm no N+1 regressions on the largest admin lists.
  - If Kysely is chosen, two connection pools will address the same database. On the
    production Dokku Postgres this must not silently double the connection count.
  - Two identifier mappers (`knexSnakeCaseMappers` and `CamelCasePlugin`) serving the same
    tables is a correctness risk worth an explicit test on real column names such as
    `foundedAtYear`, `adminEmailNotifications`, `baseurl` and `postalcode`.
  - Node's type stripping requires erasable syntax only; a contributor reaching for an enum
    or a decorator will break `npm start` rather than the build, which is a less obvious
    failure mode. Worth a note in the package README.
- **Assumptions.**
  - No client outside this monorepo depends on the API's undocumented query surface.
  - `feathers-authentication-management`, `@feathersjs/authentication-local` and the
    passport/JWT stack continue to work against hand-written services; the `users` service
    migration in Feature 7 should be scheduled with that integration in mind, as it is the
    most entangled of the public services.
- **Open question.** The Feature 6 pilot decision (knex + Kanel vs Kysely + `kanel-kysely`)
  is deliberately unresolved in this spec and must be settled — and recorded — before
  Feature 7 begins.
